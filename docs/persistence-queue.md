# 有序持久化接口：提交、执行与完成

本文记录后台磁盘发布的第一阶段；后续[磁盘线程与非阻塞主循环](background-persistence.md)已通过可选执行方式接入。[`PersistenceQueue`](../src/raft/persistence_queue.h) 已提供不可变任务、串行执行令牌、有界资源和完成结果；`QueuedStore` 用于兼容原有同步接口并测试确认边界。默认 `cluster::Server` 仍直接使用同步 `FileStore`；本文中的 169 项和证据属于接口阶段，当时没有后台运行模式或性能收益结论。

## 三个不同的成功

| 接口 | 成功含义 |
| --- | --- |
| `Submit(mutation)` | 已接收并复制任务；尚未执行，也未落盘 |
| `ExecutePersistence(...)` | 现有同步存储调用返回；只有该调用成功才满足其落盘条件 |
| `Complete(ticket, result)` | 完成报告的令牌合法并被接收；实际存储结果在 `Completion.status`，不能把报告接收成功当作落盘成功 |

调用者先提交任务，由一个消费者 `TakeNext`／`WaitNext` 取出，调用同步磁盘接口，再上报实际结果。协议所属线程按顺序领取 `TakeCompletion`。当前队列只负责持久化任务顺序，不替调用者证明存储已执行，也不负责多数派提交、任期校验或状态机应用；这些仍是确认请求成功之前必须满足的条件。

任务覆盖 hard state、日志后缀替换、快照与剩余日志的原子发布。提交时深复制输入，消费者持有 `shared_ptr<const PersistenceMutation>`；调用者随后修改原始字符串或 vector 不会改变任务。磁盘调用在队列锁外执行，任务不包含任意回调或指向可变 Raft 状态的引用。

## 顺序、身份与资源

每个队列绑定一个磁盘存储实例，最多派发一个任务。前一个完成后才派发后一个，完成结果也按提交顺序领取。消费者不得对同一个任务重复执行磁盘调用；网络重试与客户端超时不能触发持久化重放。

令牌由进程内唯一的 stream ID 和递增 sequence 组成。旧队列、重复、尚未派发或乱序的完成报告均被拒绝，当前任务保持原状。stream ID 不是磁盘 checkpoint generation，不保存到磁盘；新进程没有可继承的旧线程完成通知，重开存储也必须创建新队列。

默认最多 64 个未领取结果的任务、64 MiB 计费字节。操作数限制包含待执行、执行中及已完成但尚未领取的任务，防止完成结果堆积。字节预算按每任务 64 B、后缀头 8 B、每日志项 24 B＋命令长度、快照头 24 B＋快照内容和后缀计费；加法在剩余预算内检查。它是确定性的输入预算，不是分配器 RSS 的精确估算。队列外保留的输入、消费者持有的任务引用、存储编码缓冲仍须由集成层控制。

满载时返回 `BUSY`，不复制新任务、不消耗序号、不执行存储。完成槽和“未派发”失败消息在接收时准备，报告实际 I/O 结果和传播失败时不再新增结果槽。接口受互斥锁保护；协议结果只有一个有序领取者，磁盘侧只有一个串行消费者。

## 失败与停机

一次已派发任务失败后，队列停止接收和派发。失败任务的 `dispatched=true`：它可能已完成部分发布，甚至已经同步到磁盘，只是成功通知之前出现错误。排队后继得到 `SHUTDOWN` 且 `dispatched=false`，明确表示没有派发。

不能把失败状态解释为磁盘未发生修改，也不能在原实例上重试。关闭失效存储后重新恢复，再创建新队列。存储抛出的标准或未知异常统一转为 I/O 失败，后续同样停止执行。

`StopAccepting` 仅关闭入口，已接收的任务仍按序排空；它不会把正在执行的任务改成成功或取消。队列本身不创建线程，也不隐式执行 I/O。集成层必须完成或处理全部任务、唤醒并结束消费者、等待线程退出，之后才能销毁队列和存储。

`WaitCompletion` 只供单个有序调用者等待队首结果，不提供“超时后撤销写入”。客户端超时后的业务结果仍可能未知，后续完成通知不能重放该写入。

## 同步兼容与实际测试

`QueuedStore` 保持 `HardStateStore::Save`、`LogStore::ReplaceFrom / SaveSnapshot` 的原有“返回 OK 前必须完成持久化”契约。它会阻塞调用者，必须由另一个执行上下文驱动队列；不能将它接到现有 owner 线程后直接宣称异步化。原有同步接口将任何存储失败视为实例不可继续使用，适配器接收失败也沿用这个保守处理；未来非阻塞入口应先检查任务接收结果，再推进相应状态。

新增 15 项组件测试，其中使用真实 `Node`、`RaftLog`、`FileStore` 和受控完成通知，检查：

- 选举自投票未完成时，不产生 RequestVote；磁盘调用结束但完成通知尚未交付时，仍不产生消息。
- 投票回复等待 term／vote；AppendEntries 的成功回复及已提交条目等待 hard state 和日志两次持久化完成。
- 快照边界在原子发布及完成通知之后推进。
- journal 已同步后注入错误，节点不能确认选举，后继日志任务不派发；重开磁盘仍能读到该次可能已落盘的 term。
- image／journal 两种模式的实际文件字节与同步执行相同，重开后的快照、hard state 与日志一致。
- 输入所有权、并发接收、有界积压、停机排空及错误完成令牌。

这些测试控制存储任务与通知的先后顺序，不以睡眠时长推断落盘完成。它们不替代后续实际后台 owner 接入后的客户端确认、线程竞争、强杀与恢复验收。

最终普通／ASan＋UBSan 完整回归均为 169/169，分别耗时 66.83／82.29 秒，sanitizer 开启泄漏检测。首次普通回归中的旧追踪测试出现零持久化交集：快速磁盘上的自然短负载允许这个结果，原测试却要求必须大于零。现复用测试专用 I/O 注入库，仅在追踪活动期间把 Leader 的 Raft 文件同步延迟 5 ms，保留交集断言并核验实际文件同步交集。原有资源测试默认的 250 ms 延迟不变；该条件不用于性能测量。[完整记录](../benchmarks/published/persistence-queue-20261026/README.md)保留修正前后结果。

## 后续集成的验收条件

下述 1–3 项已在[后台执行阶段](background-persistence.md)接入并通过本机故障测试；第 4 项增加了任务和请求依赖令牌，旧同线程分析会拒绝异步输入，完整归因及第 5 项的云端收益对照仍待验收。

1. 给 Raft owner 增加明确的待持久化状态与完成处理，区分计算出的效果和可对外释放的效果。不能通过把原同步 `Save` 提前返回 OK 来实现。
2. 由每节点一个磁盘线程消费队列，完成后唤醒 owner；owner 不在原处理路径等待 `future.get()`，并继续满足 ReadIndex 的本轮多数派与应用位置条件。
3. 处理提交拒绝、任期变化、旧完成通知、快照／journal 代次、失败停机与对象生命周期。存储指标读取也要避免在 owner 上等待磁盘锁。
4. 异步磁盘线程的 TID 将与读处理线程不同。现有“同 TID 区间交集”不能直接作为新路径的等待归因，需增加任务令牌与请求依赖的关联。
5. 先通过真实后台路径的强杀、磁盘失败及恢复测试，再做关闭追踪的重复三机对照，报告尾延迟、未发时刻及 CPU／RSS；收益成立后才延长实验窗口。
