# 2026-10-22 本机读调度、检查点与故障验证

本轮继续使用一台电脑上的三个独立测试进程，不租用服务器。改动与结果只适用于固定三个 voter、单 Raft Group、回环网络及现有容量限制。

本轮已完成：普通与 sanitizer 各 125 项回归、磁盘补充 43 项、72 轮性能对照，以及一小时 3,302 轮故障活动。均衡读写吞吐提高约 19.7%；15 MiB 场景默认吞吐约 6.62 倍，但同步检查点的单次暂停与部分负载的更高分位延迟仍需继续改进。

## 实现

### 读确认与写复制重叠

运行时为已收到的 GET 记录任期和先前写入的应用位置，先登记新的 ReadIndex 轮次，再持久化同批写提案。Raft 核心把 AppendEntries 的构造推迟到 `TakeMessages()` 交付传输层时，因此新 context 可以与尚未交付的写复制共用请求。已经交付的旧请求不改 context，旧回复和重复旧回复不能完成之后收到的读。

返回读结果仍要求当前任期已提交条目、新 context 的多数派确认，以及状态机达到 ReadIndex 和先前写入两个应用位置。失去领导权、任期变化、超时和有界等待额度的处理保留。该路径不使用 Leader lease。

`status` 新增 read_overlapped_requests、append_requests、read_append_requests 和 read_append_with_entries，用于检查实际是否合并了复制，而非仅凭吞吐推断。

### 大活跃集合的检查点成本

默认 `--snapshot-policy adaptive`：达到条目阈值时，还要求保留日志字节至少为 `min(snapshot_bytes, live_snapshot_bytes / 4)`；原字节阈值仍独立触发。小集合保持原有条目回收节奏，大集合减少少量小更新引发的全量重写。`--snapshot-policy fixed` 保留旧策略，可在同一二进制内进行对照。

CRC32 用查表替代逐字节八次位运算，保持 IEEE 多项式、初始值、取反及磁盘字节格式。独立的逐位编码器检查二进制 payload 和快照的校验和兼容性。检查点仍同步生成；本轮没有把落盘确认移到后台或删除文件／目录同步。

新增 snapshot_pause_ns 和 snapshot_pause_max_ns，覆盖状态序列化、验证、检查点同步及发布。累计最大值包含预填充，不能相减得到计时窗口最大值；旧版本缺少这些计数，不能把缺失的零值当作零成本。

### 故障与跨轮次恢复检查

测试专用 I/O 库新增正常短写、写入半条日志后 EIO，以及副本同步变慢。验证完整写循环、失败节点停止服务、已确认值保留和故障解除后的追赶。注入只影响独立测试进程的 Raft 文件。

持续故障活动保留六类故障与有界逐 key 历史模型，新增最多 32 个循环更新的持久 key。每轮先检查此前已确认值经历本轮故障后仍可读取，再确认新的更新；结束时全节点 SIGKILL／重启，重新检查完整集合。它们与并发模型的操作计数分开统计。未知写入仍以可选、无完成时间上界保留。

## 实验方法

冻结上一轮默认版本和本轮构建，保存源码归档、构建环境与二进制 SHA-256。测试数据位于工作区磁盘，测试、编译和故障活动不与性能测量并行。

读路径实验交错比较旧默认、新默认与新版本 log 读路径，五种负载各重复三次，每轮计时 15 秒。当前同二进制的两种读模式可比较 ReadIndex 开销；跨版本结果包含本轮所有改动，不能把收益全部归因于单一调度修改。

检查点实验分别预填充 1／8／15 MiB 不常修改的 value，再由八个客户端读写各自的小热 key，保留旧版本、新版本 fixed 和新版本 adaptive 三种对照。后两者仅改变快照策略，可用于隔离频率调整的影响。每轮结束后强杀三个节点，重启并核对全部 cold／hot 最终值；预填充与恢复均不计入吞吐与请求延迟。

逐请求样本保留完成时间、延迟和读写类型；核验会重新计算 P50／P95／P99／P99.9／最大值、逐秒分桶、操作比例和持久化差值。汇总取独立运行统计量的中位数。三个节点与负载发生器共享四个逻辑 CPU，故障活动另使用链路代理；没有隔离后台服务、固定 CPU 频率或磁盘缓存，因此这些是开发对照，不是生产饱和或扩展性数据。

## 结果

性能部分已完成 **72 轮、4,353,146 次计时操作**，所有 GET 和请求状态检查通过，原始样本核验通过。读路径 45 轮、3,304,838 次操作；大状态 27 轮、1,048,308 次操作。预填充、预热、恢复校验均不计入这些次数。

### 读路径

下表为三轮运行统计量的中位数，“旧／新”均为默认 journal／ReadIndex：

| 场景 | 旧 ops/s | 新 ops/s | 吞吐变化 | 旧 P99 ms | 新 P99 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 纯读，128 B、64 key | 14710.6 | 15114.2 | +2.7% | 1.481 | 1.489 |
| 50% PUT，128 B、64 key | 3403.1 | 4073.5 | +19.7% | 5.637 | 4.427 |
| 90% PUT，128 B、64 key | 3308.9 | 3672.9 | +11.0% | 5.903 | 5.078 |
| 50% PUT，8192 B、64 key | 2158.3 | 2876.5 | +33.3% | 12.048 | 7.407 |
| 50% PUT，128 B、1024 key | 3158.4 | 3768.7 | +19.3% | 8.246 | 6.238 |

纯读仍为零持久化字节、零保存次数、零日志增长；纯读的延迟变化很小，不据此声称显著改善。均衡场景三轮共 91,132 次新版本 GET，其中 50,240 次在先前写入尚未应用时开始确认；记录到 68,495 个同时携带读 context 和日志条目的 AppendEntries，支持确认与复制实际重叠的判断。

同一新二进制的 log 读对照在均衡场景为 3700.0 ops/s、P99 4.643 ms，本轮 ReadIndex 在该条件下吞吐高约 10.1%。但写多读少和更多 key 场景，ReadIndex 吞吐仍分别低约 2.9% 和 1.7%，P99 也较差；两种读模式保留。

**更高分位并非全部改善。** 均衡场景的 P99.9 中位数从 8.332 增至 10.859 ms，三轮最大延迟的中位数从 13.029 增至 26.026 ms。单轮新版本最大值为 28.715 ms。它说明吞吐与 P99 的收益没有消除长尾，也不能由三轮未隔离资源的实验断定全部原因。完整对照和每轮值保留在[读路径汇总](../benchmarks/published/local-followup-20261022/reads/summary.md)。

### 大活跃集合与检查点

预填充的 MiB 指冷 value 的总字节，不包含 key／Protobuf 开销；热集合为 64 个 128 B value。下表比较旧默认和新默认，同样为三轮统计量的中位数，写入字节累加三个副本：

| 冷 value 集合 | 旧 ops/s | 新 ops/s | 旧 P99 ms | 新 P99 ms | 写入 B/操作：旧 → 新 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 MiB | 2670.9 | 4059.4 | 15.847 | 4.677 | 12649.5 → 1344.2 |
| 8 MiB | 1057.1 | 4151.5 | 168.699 | 4.517 | 96864.2 → 2345.2 |
| 15 MiB | 612.8 | 4054.6 | 320.959 | 3.959 | 173845.0 → 4190.3 |

15 MiB 场景新默认吞吐约 **6.62 倍**，应用观测写入字节／操作下降约 **97.6%**。该场景旧版 P99 的三次实测分别为 349.722、320.959、186.212 ms，新默认为 3.703、3.959、4.764 ms；原值保留以展示波动。

同一新二进制仅切换 fixed → adaptive：15 MiB 场景吞吐从 1201.2 增至 4054.6 ops/s，P99 从 120.361 降至 3.959 ms，写入字节／操作从 148467.2 降至 4190.3。三节点检查点次数的中位数从 173 降至 15。仍使用 fixed 时，相比旧版本的编码／CRC 累计成本由约 1530.5 降至 388.4 µs/操作；它包含编码与实际批次变化，不能解释为单独的 CRC 函数基准。

新默认 15 MiB 场景的 P99.9 为 8.513 ms，三轮最大值的中位数为 88.435 ms；**全部三轮中仍出现 163.717 ms 的单次请求**，观测到的单次快照暂停最高为 159.000 ms。减少频率与优化校验没有使检查点异步化。详见[全部三策略对照](../benchmarks/published/local-followup-20261022/snapshots/summary.md)。

### 同轮数据恢复

27 个大状态运行均全节点 SIGKILL／重启，共核对 **29,376 个最终值**。每个冷 key 和每个客户端热 key 的最后确认版本均一致；保留实际恢复值的长度分隔 SHA-256，核验器会从工作负载和最终版本独立重建预期摘要。

另用本轮与上一轮两个 v3 二进制，在同一份数据上按新／旧／新／旧／新五阶段整组切换。每阶段写入、删除、等待副本应用后强杀；独立 Python zlib 检查全部三个副本的检查点、journal 头和记录 CRC。最终新版本恢复 59 个值、5 个删除状态均通过。该检查只覆盖这两个 v3 版本，不承诺旧 v1/v2-only 程序可读，也不是滚动升级验收。工具为 `scripts/check-followup-compatibility.py`。

从强杀到全部最终值核验完成的中位时间，1／8／15 MiB 场景旧版分别约为 0.741／1.117／1.491 秒，新默认为 0.697／1.097／1.371 秒。本组实验没有观察到完整核验显著变慢；计时包含进程启动、选举、重放和逐值 RPC 校验，不能解释成纯磁盘恢复速度或可用性 SLA。

自适应策略确实保留更多后缀：15 MiB 新默认三轮结束前各副本最大保留条目数为 4947／5910／813，对应约 0.866／1.034／0.142 MB；同二进制 fixed 为 43／97／41。`restart_to_committed_leader_seconds` 只表示观察到 Leader 且 commit index 恢复到强杀前下界，未单独验证本任期读门槛，不当作服务就绪时间；之后的全部 GET 均通过真实 ReadIndex。

### 延长故障活动

正式活动持续 **3601.40 秒（约一小时）、3,302 轮**，共 **178,308 次尝试、176,543 次模型操作**，全部通过检查。**2,472 次结果未知的写入**仍按可选、无完成时间上界保留，没有把超时当成未写入。

| 故障 | 轮数 |
| --- | ---: |
| Leader SIGKILL／重启 | 551 |
| Follower 隔离／恢复 | 551 |
| 有向链路隔离／恢复 | 550 |
| 链路延迟／恢复 | 550 |
| 全节点强杀／重启 | 550 |
| Leader SIGSTOP／SIGCONT | 550 |

跨轮次已确认持久值共核对 **105,168 次**（含最终恢复后的 32 个值），另有固定锚点检查。结束时再次强杀全部节点、重启，固定锚点及 32 个最新持久值均恢复。并发模型仍每 key 最多九次操作；这些顺序持久值检查与模型操作分开计数。

测试种子固定场景与操作选择，OS 调度仍不确定。原始尝试、模型输入、故障开始／解除时刻、确认与恢复观测、节点日志及源码归档均保留。核验会从尝试重新构造模型输入，重放全部有界逐 key 历史，检查跨轮次持久值与新旧版本兼容记录，并确认性能与故障活动的生产编译输入及被测二进制一致。

## 仍保留的边界

检查点仍在节点工作线程同步生成，单次较大检查点仍可能阻塞请求；降低频率不能消除所有最长暂停。自适应策略会保留更多后缀条目，须同时观察重启重放成本。活跃编码快照上限仍为 16 MiB，逻辑状态上限仍为 64 MiB。

有限故障历史、sanitizer 和有界模型检查不等于形式化证明。跨机器、宿主机故障、真实断电、多日运行、成员变更、认证和跨 key 事务尚不属于本轮验证结论。

## 复现

先保存旧版本二进制及对应源码，再构建本轮；运行时不要覆盖被测二进制：

```bash
python3 benchmarks/local_followup.py --baseline /absolute/path/to/prior/yewukv-node \
  --node build/bin/yewukv-node --suite reads --duration-seconds 15 --repeats 3 \
  --output benchmarks/results/my-followup-reads
python3 benchmarks/local_followup.py --baseline /absolute/path/to/prior/yewukv-node \
  --node build/bin/yewukv-node --suite snapshots --duration-seconds 15 --repeats 3 \
  --output benchmarks/results/my-followup-snapshots
python3 scripts/cluster-soak.py --node build/bin/yewukv-node --client build/bin/yewukv-client \
  --output benchmarks/results/my-followup-faults --duration-seconds 3600
```

`--duration-seconds 86400` 可用于后续 24 小时活动；本轮的实际运行时间以结果与 manifest 为准。保持运行机器、磁盘空间和电源可用，保留失败目录和进度文件；多日运行结果不能由较短测试推算。
