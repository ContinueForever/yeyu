# 有界副本等待修复：三机新旧对照（2026-10-26）

有界等待消除了本轮小状态后台路径的大部分额外重试尾部，但尚未通过全部性能门槛。1 MiB 的每轮 P99.9 中位数从 491.046 降至 46.344 ms；15 MiB 从 472.232 降至 244.726 ms，仍为旧值的 51.82%，没有达到预先要求的减半。服务默认继续使用同步磁盘。

正式 18 个 30 秒窗口共 540 秒计时、906.679 秒墙钟。318,263 次已发请求全部成功，另外 5,737 / 324,000 个计划时刻未发（1.7707%）。每轮独立目录并整组重启核对，18 次通过。此前三个两秒预检另有 3,600 次成功、零未发、三次重启通过，不合并进正式数据。[公开证据](../benchmarks/published/peer-disk-20261026/README.md)保留所有请求、资源、恢复值哈希、实际启动参数与源码。

## 修复与因果范围

[有界副本等待](peer-disk-admission.md)先让 Node 处理高任期隔离；如果磁盘屏障暂时拒绝准入，owner 保存至多两个请求，每个远端最多一个，截止时间 300 ms。磁盘完成后先重新准入副本请求，再开始新的本地磁盘工作。确认仍等待所需持久化屏障，满队列和过期请求沿用现有失败语义。

将本次云端实际使用的新旧二进制放入本机可控检查点实验，阻塞一个 Follower、临时隔离另一个，使写入必须经过被阻塞副本。TCP 记录关联实际请求序号与响应：旧程序返回一次 BUSY，501.508 ms 后才再次发送复制请求；解除磁盘闸门到写入确认为 411.490 ms。新程序没有 BUSY，解除到确认 6.458 ms，等待请求成功准入；两者整组重启核对均通过。此前本机构建程序的 424.114／4.226 ms 初步结果也完整保留。

这是可控条件下的机制验证。它不能把云端每个慢请求归为同一原因，也不能将本机 6.458 ms 当作云端复制延迟。

## 比较配置

- 三种条件：旧后台（核心 `66bd2a9`）、新后台（`834bb43`）、新同步（`834bb43`）。新同步是同期控制，避免把不同时段的噪声当成修复收益。
- 1／15 MiB 各三组，每组包含三种条件，每种顺序位置各出现一次；大状态反向排列，共 18 轮。固定后台 KV 快照编码器、journal、ReadIndex、adaptive、128 条／1 MiB 快照触发和 4 MiB journal 检查点阈值。
- 32 连接、600 offered rps、50% 写、128 B 热值、预热一秒，实际请求为 158,894 PUT／159,369 GET。每连接最多一个未完成请求；忙时跳过的计划时刻单列，不能据此宣称严格开放环容量。
- 无追踪参数和追踪记录器。Leader 固定节点 2，C++ 发压与控制程序共置 Follower 3。三台 ECS 各两个逻辑 CPU、约 3.54 GiB MemTotal；节点服务与发压服务分别限一个 CPU／512 MiB，原服务同时运行。
- GCC 13.3、RelWithDebInfo，云端构建关闭测试。新旧实际程序、对应源码包与十一项执行工具均以 SHA-256 绑定；云端核心和工具冻结为 `834bb43`，后续 `4193bb0` 只修正两个测试文件，生产源码逐文件相同。

这些窗口来自同一次约十五分钟活动，不能当作跨天独立重复。上一轮负结果仍保留在[旧对照报告](cloud-async-disk-20261026.md)；本次收益使用本次同期旧后台控制计算。

## 验证、测试修正与后续长窗口

本机普通 188 项、ASan＋UBSan 189 项通过；新增有界等待与计划相关四项通过，五项纯计划检查通过。核心首次 push CI 通过，首次 PR CI 在两个旧测试中失败：追踪测试两秒采到 96 个 GET，低于人为的 100 个门槛；配置发布调用失败且旧测试隐藏了 stderr，现有日志无法确认其精确原因。完整失败记录已保留。

`4193bb0` 改为按实际 GET 数检查完整关联，并让配置发布使用应用既有的 1500 ms 默认预算，保留 500 ms 探测与详细错误输出，没有自动重放结果未知的写入。相关普通／ASan 各四项通过；修正后的 [push CI](https://github.com/ContinueForever/yeyu/actions/runs/40265323899) 与 [PR CI](https://github.com/ContinueForever/yeyu/actions/runs/40265328907) 均通过。七项离线负例会重算文件哈希后继续伪造数据，独立核验仍必须拒绝错误分位数、实际模式、请求日历、CPU 计数、恢复值、队列计数与提前确认。

在数值门槛判定失败后、长实验启动前，明确将长实验目标改为“可选后台路径的正确性与稳定性”，保留初始同步选择及其哈希、失败门槛和默认同步。六小时计划为 360 个一分钟窗口、六阶段，KV 编码器 sync／background、1／8／15 MiB，轮换 0／50／90% 写入。该运行现已完成[六小时稳定性独立核验](background-soak-20261026.md)：360 个窗口、12,836,802 次成功请求，123,198 个未发时刻、六次阶段恢复通过；它不改变本轮性能门槛失败，也不代表多日稳定性。

公开客户 gzip 字节保持不变；诊断里的机器地址、路径、主机名一致脱敏并记录前后哈希。原始业务值、控制 token、私钥、数据库和程序不公开。独立核验只执行当前仓库代码，不执行归档工具。此结果不包含真实断电、多日运行、独立发压容量或其他负载承诺。
