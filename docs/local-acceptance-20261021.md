# 2026-10-21 本机快照、故障与性能验收

本文保留优化前 image 持久化／日志读路径的历史验收。后续增量 journal、ReadIndex 和配置应用的实现与验证见[本机优化报告](local-optimization-20261021.md)。以下测量值与限制对应原实验版本。

本轮实现了原子 KV/Raft 快照、日志前缀回收、分块快照传输、重启恢复、活跃数据容量保护与连接回复缓存限制，并增加持续故障和多负载性能工具。

所有实验均为同一台机器上的三个进程，不能据此声称宿主机故障可用性、真实断电恢复或生产性能。新实现保留固定三节点、单 Raft Group 和日志读语义。

## 15 分钟真实进程故障活动

最终运行时长 900.80 秒，共 948 轮、51,192 次操作尝试，其中 50,970 次有状态意义的操作纳入逐 key 寄存器模型并通过检查。其余为明确拒绝或结果未知的读。794 次结果未知的写入仍作为可选、无完成时间上界的操作保留在模型中，没有将超时简单当作“未写入”。

| 故障 | 轮数 |
| --- | ---: |
| Leader SIGKILL 后重启 | 190 |
| Follower 隔离后恢复 | 190 |
| 有向 peer 通道隔离后恢复 | 190 |
| peer 通道延迟后恢复 | 189 |
| 全节点强杀并重启 | 189 |

每轮三个客户端各做 18 次 PUT/GET/DEL，使用六个新 key；同一 key 的并发操作不跨轮截断，因此每 key 最多九次操作，适合现有有界穷举检查器。每轮保留完整尝试记录、模型输入、故障时刻及状态。最后再次全节点重启并检查预先确认的数据。

逻辑模拟器严格按种子重放；真实进程的种子只固定场景与操作选择，OS 调度仍有不确定性。这些有限测试不能替代形式化证明或多日运行。

清理了编排器在重复重启中的父进程日志句柄与已结束代理线程引用。补充测试把协调进程文件句柄上限设为 128，重启副本 100 次，父进程句柄从 14 到 12，最大 14；受影响的四项进程测试在普通和 sanitizer 构建下各再次通过。[资源记录](../benchmarks/published/local-20261021/harness-resources-20261021.json)。

扩大测试曾发现“Follower 已压缩前缀但 Leader 丢失确认，持续向旧位置回退”的活性问题。已修复边界 term 匹配后的向前探测，并保留种子 56 和独立回归用例。

## 性能矩阵

七种负载每种重复三次，每次至少测量 10 秒并等待最后在途请求完成，共 21 轮、282,746 次计时操作，所有轮次通过请求 ID、状态及 GET 值校验。预填充和每客户端 20 次预热 GET 不计入延迟和吞吐。

环境为 Ubuntu 虚拟机、4 个可用逻辑 CPU、约 8 GiB 内存，GCC 15.2、RelWithDebInfo、无 sanitizer；三节点和最多四个 Python 发压进程共享本机 CPU 与磁盘。原后台集群空闲常驻，未固定 CPU 频率、磁盘缓存或其他系统服务，因此是开发基线。

| 场景 | 客户端 | PUT 比例 | value 字节 | 活跃 key | 吞吐中位数 ops/s | 各轮 P99 中位数 ms | 服务端平均核数 | 客户端平均核数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 单客户端 | 1 | 50% | 128 | 8 | 422.6 | 3.856 | 0.54 | 0.03 |
| 读多 | 8 | 10% | 128 | 64 | 1749.6 | 7.137 | 0.68 | 0.10 |
| 均衡 | 8 | 50% | 128 | 64 | 1695.6 | 7.312 | 0.71 | 0.10 |
| 写多 | 8 | 90% | 128 | 64 | 1650.1 | 7.588 | 0.74 | 0.10 |
| 大 value | 8 | 50% | 8192 | 64 | 225.1 | 65.539 | 1.68 | 0.02 |
| 更多 key | 8 | 50% | 128 | 1024 | 809.9 | 15.308 | 1.32 | 0.05 |
| 更多客户端 | 16 | 50% | 128 | 128 | 2891.6 | 8.489 | 0.80 | 0.16 |

P99 是三轮 P99 的中位数，不是合并样本的 P99。CPU 核数为 CPU 秒数／墙钟秒数；节点 CPU 与持久化计数包含测量后的短暂复制收敛。RSS 为每 250 ms 采样的三进程之和，共享库页会重复计入。逐秒 timeline 用完成时间分桶，最后不足一秒的窗口不能与完整一秒直接比较。

这些是场景比较；单客户端、更多客户端场景也改变了总 key 数，不能据此宣称线性扩展性或服务端已饱和。

实测大 value 场景降至约 225 ops/s，P99 约 65.5 ms，三节点平均 CPU 约 1.68 核，发压客户端约 0.02 核。均衡场景约 1696 ops/s、P99 7.3 ms，服务端约 0.71 核。更多 key 场景也明显变慢。结合编码镜像写入量与实现，这是全量镜像编码、校验和重写成为重要瓶颈的证据；客户端 CPU 占用较低，当前数据不支持把下降归因于 Python CPU 饱和。精确函数级 CPU 归因仍需后续 profiler。

GET 仍追加并复制日志，因此读多场景没有数量级的吞吐提升。快照解决了历史日志增长，下一项存储优化应评估分段追加日志，读路径可另行评估 ReadIndex；本轮未用放宽一致性换取吞吐。

### 同负载快照阈值 A/B

相同二进制、8 个客户端、64 个 key、128 字节 value、50% PUT，批大小 32；仅切换快照条目阈值。两种配置的字节阈值均为 64 MiB，交错运行三轮、每轮 10 秒。大条目阈值配置在这三轮中没有生成快照。两者都保留相同的落盘、多数派提交和日志读语义。

| 配置 | 吞吐中位数 ops/s | 各轮 P99 中位数 ms | 服务端平均核数 | 三节点编码镜像写入量中位数 |
| --- | ---: | ---: | ---: | ---: |
| 每 128 个已应用位置触发快照 | 1695.7 | 7.418 | 0.71 | 258,732,261 字节 |
| 本轮不触发快照 | 506.2 | 32.997 | 1.59 | 1,340,000,458 字节 |

在该负载下，吞吐约为 3.35 倍，P99 降低约 77.5%。两种配置合计 66,024 次计时操作；与正式矩阵合计 27 轮、348,770 次计时操作，原始样本、操作计数与逐秒分桶计数已逐一交叉核对。

不回收配置三轮的第一个完整秒分别为 1141、1105、1118 ops/s，最后完整秒降至 264、299、312 ops/s；回收配置对应为 1651／1685、1686／1708、1660／1711 ops/s。这个短时对照直接显示历史增长导致的性能衰退，以及本轮回收方案的改善。它不能证明无限运行或大活跃集性能。

编码镜像字节是成功发布镜像的用户态字节计数，不是磁盘物理扇区写入量，也不是 fsync 次数。A/B 数字不能与早期单节点内存读、不同负载或不同语义的基准直接比较。

## 现有后台集群切换

隔离验收完成后，已先备份原有三节点目录，再统一停止／启动全部节点，切换到与故障活动和性能矩阵相同的二进制。原有 2 个活跃 key 的值逐一比较一致，未新增或删除业务 key；用 PING 驱动实际快照，并确认三个后台节点均报告正数 snapshot_index。

## 仍然存在的边界

活跃 KV 的编码快照上限为 16 MiB，原子镜像上限为 64 MiB。默认每 128 个已应用位置或 1 MiB 后缀触发快照，批次可越过触发阈值。每次持久化仍重写整个快照及保留后缀，存在写放大；接收快照仍在内存中组装。GET 仍经过多数派日志提交，尚未使用 ReadIndex。

ENOSPC/EIO 是只作用于测试节点的系统调用错误注入，没有填满整台机器的磁盘。跨机器、独立故障域、真实断电、多日稳定运行、TLS、分片和成员变更均未在本轮验收。
