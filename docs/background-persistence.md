# 后台磁盘执行与非阻塞 Raft 主循环

2026-10-26 接入可选 `--disk-executor background`。每个节点由一个磁盘线程执行原来的同步 `FileStore`，Raft 所属线程通过准备状态和完成通知推进，不等待 `future.get()` 或磁盘锁。默认仍为 `sync`；当前交付的结论是确认与恢复边界通过本机验收，云端性能收益须另做对照。

## 使用

在 `yewukv-node` 原有节点参数后增加：

```sh
--disk-executor background
```

`--disk-executor sync` 使用原来的同步路径。两种执行方式可以分别与 `--raft-store journal|image`、`--snapshot-encoder sync|background` 配合；磁盘格式不变。快照编码线程负责 KV 编码，磁盘线程负责文件写入与同步，二者是独立开关。已有云服务尚未切换，应在独立实验目录验收后再决定默认配置。

`status` 新增 `disk_executor`、`persistence_pending`、`admitted_last_index`、`staged`、`persistence_queue_operations / bytes`。`last_index` 仍表示核心已接收完成通知的持久日志位置；`admitted_last_index` 还包含已接收但尚未确认落盘的本地提案位置，不能用它计算自身持久副本。磁盘指标由执行线程在每次存储调用结束后更新缓存，状态查询不会等待 `FileStore` 的 I/O 锁。

## 状态与确认顺序

`Election` 和 `RaftLog` 提供 `Prepare… / Advance…`。准备过程验证输入、准备分配和拥有数据，不把未来任期、投票、日志或快照发布到可见状态。`Node` 将任务交给[有序持久化队列](persistence-queue.md)，只有同一 stream／sequence 的真实完成结果才能驱动后续状态转换。

| 操作 | 对外效果之前的条件 |
| --- | --- |
| 发起选举 | term 与自投票持久化完成，之后才发送 RequestVote |
| 同意投票 | 新 term／vote 持久化完成，之后才回复 granted |
| 接收更高任期 AppendEntries | 先持久化 hard state，再持久化日志后缀，之后才成功回复或交付新提交条目 |
| 本地提案 | 接收时预留索引；日志持久化完成后才进入复制；多数派提交并按序应用后才返回客户端 OK |
| 快照安装 | 原子发布快照与保留后缀完成后，才安装状态机和确认最后一块 |
| 本地快照 | 提交发布任务时获取当前保留后缀；完成后才推进快照边界 |
| GET | 当前任期提交门槛、本轮相关联多数派及应用位置条件同时满足；应用位置还必须覆盖先前已接收提案与排队写入 |

启用队列时，`Node::Campaign / ProposeBatch / Compact` 的成功仅表示接收；同步模式仍保持原语义。原 `HardStateStore / LogStore` 的“返回 OK 前必须持久化”契约完全保留，没有用提前返回伪造完成。集成者应调用 `ReceiveAsync`，并在所属线程调用 `AdvancePersistence`；回调仅由该所属线程执行。接收失败不调用回调，不预留索引，也不因一次未派发的 BUSY 污染日志实例。

同一节点最多一个待确认的磁盘任务。写入等待时，所属线程仍处理状态、请求期限、当前持久前缀的心跳／副本回复，以及该前缀上的新鲜 ReadIndex 多数派确认。新写入在有界业务队列中等候。该阶段没有实现磁盘并行、推测复制或跨批次 group commit；原有单批最多 32 条命令的同步摊销保持不变。

## 任期变化、失败与停机

来自配置内成员的更高任期消息在磁盘忙时立即撤销旧 Leader 的可见身份、读确认和待发消息。已派发的旧写入不能取消：完成后更新真实持久状态，但不会恢复旧 Leader、发出旧任期的肯定回复或确认旧客户端。即使该消息因 BUSY 没被接收、传输方没有重试，所属线程仍会将所见的最高任期持久化。

同任期的有效 Leader 请求同样立即停止本节点的旧 Leader／Candidate 行为。原来收到的已提交条目仍须按序交付应用；不能为抑制旧回复而丢掉应用事件。服务端在应用前也按提案所属任期清理旧客户端索引映射，防止新 Leader 的替换日志误确认旧请求。

任务接收后出现 I/O 错误或异常，包括“字节已同步，但发布成功通知前失败”，都会停止该存储流与节点；不能重试或把它解释为肯定未写入。客户端超时不撤销已接收写入。停机先结束所属线程的提交，再排空已接收的磁盘工作并等待线程退出，之后才销毁存储；异常退出后由原有恢复逻辑校验并重建。

运行时队列限制为一个任务、128 MiB 确定性输入预算，包含未领取完成结果。业务待处理总数和事件队列仍使用原有上限。预算不是整个进程 RSS 上限；准备状态、编码缓冲、KV 冻结值和消费者保留引用仍有额外内存开销。

## 追踪与指标解释

磁盘追踪增加 `task_stream / task_sequence`，ReadTrace 增加 `persistence_stream / persistence_sequence`，后者记录先前本地写入对应的应用位置依赖。多个磁盘阶段可以属于同一个任务；任务序号不是 Raft 日志索引、持久化事件序号或 checkpoint generation。

`persistence_timeline.py` 的旧版同线程区间交集分析明确拒绝带异步任务的输入。磁盘线程与读处理线程 TID 不同，不能据此把零交集报告为“消除了等待”。当前令牌可用于核对依赖，完整异步等待归因与跨机对照仍是后续工作。后台执行时，`snapshot_pause / publish` 计时是所属线程准备和接收发布任务的时间，完整磁盘耗时另见 `disk_*` 与任务追踪，不能拿二者混算提速。

## 本机验收

新增 16 项确定性 C++ 测试及一组真实三进程验收，包含：

- 投票和选举消息、hard state／日志两次屏障、错误和重复完成报告、接收预算不足、任期变化前后确认顺序。
- 磁盘等待期间的持久前缀复制、ReadIndex 多数派、前序 PUT 的 GET 应用位置条件；更高任期到达后无需重试也会持久化。
- 编码之后出现的新日志后缀、异步快照安装、image／journal 两种格式重开恢复，以及同步后异常的未知结果。
- 测试专用 I/O 闸门将同步暂停超过通常选举超时；状态查询继续响应，Leader 不因自身磁盘等待而停止心跳，GET 和 PUT 在释放闸门前均不能成功。
- 两种格式的写入途中 SIGKILL、已接收任务的停机排空、ENOSPC／EIO／部分 journal 写入；复用原有并发历史、隔离与 Leader 接管、ReadIndex、CAS／ABA 和快照追赶断言。

闸门只在测试注入库中存在，生产节点没有对应开关。这些是正确性验收，不是自然负载的性能结果；ASan／UBSan 也不等同于线程竞争检测。

完整普通／ASan＋UBSan 回归各 186/186 通过，分别耗时 83.26／102.67 秒，ASan 开启泄漏检测。组件 TSan 31/31 通过（新增后台执行 16 项＋已有队列 15 项），范围不包含整个服务。新增强杀测试首次使用的读取助手会重设 socket 超时，错过观察窗口；现改为有 100 ms 超时的直接窥读，不放宽“闸门释放前无响应”断言，保留修正前后日志。

最新回归与完整原始记录见[本阶段验收证据](../benchmarks/published/async-persistence-20261026/README.md)。下一步先实现异步任务依赖复算，再在三台现有 ECS 的独立目录进行关闭追踪的重复同步／后台对照；只有收益及资源代价明确后再启动较长运行窗口。
