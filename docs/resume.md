# 简历与面试说明

更新：2026-10-28。目标岗位为 C++ 后端／基础架构／存储方向实习。项目定位是固定三节点的分布式 KV 实验系统；现有实现与验证已经可以用于投递，后续重点是讲清设计、源码和实验取舍。

## 推荐简历版本

**yewukv｜基于 Raft 的分布式 KV 存储｜个人项目**

技术栈：C++17、Linux、epoll、Protobuf、Raft、CMake

- 基于 Reactor 与 Protobuf RPC 实现固定三节点 KV 服务，完成选主、日志复制、持久化恢复和快照追赶；通过 ReadIndex 多数派确认及应用屏障实现强一致读，支持 revision／CAS。
- 实现增量 journal 与有序后台磁盘执行，通过持久化完成通知推进 Raft；为繁忙副本增加有界请求等待，保留高任期撤销、落盘后回复及多数派提交边界。
- 在三机、1 MiB 冷数据、32 连接、600 rps 输入计划、50% 写条件下，将可选后台路径 P99.9 的三轮中位数由 491.046 ms 降至 46.344 ms，约下降 90.6%。
- 完成三机六小时计时验证：360 个窗口、12,836,802 次已发请求全部成功，0.9506% 计划时刻未发，六次阶段整组恢复通过；接入普通／ASan＋UBSan 各 189 项 CTest 与公开证据核验 CI。

项目时间填写实际投入的起止月份；个人职责按实际掌握与负责的部分调整。简历中放仓库链接，并保持下列指标条件可供追问。版面不足时先缩减技术栈和部署细节，保留一致性、性能修复和验证三条主线。

云端使用三台现有 ECS，发压与 Follower 共置，节点和发压服务各限一个 CPU／512 MiB。600 rps 是计划输入，不能写成系统容量；忙时跳过的时刻没有变成已发请求。六小时通过只验收本次可选路径的稳定性，不改变性能门槛失败。

六小时恢复工具在线比较了全部冷值、热值与锚值；冻结恢复文件只保留计数、revision 和状态，公开材料不能重建每一次恢复响应字节。18 轮短对照则单独保留逐值长度、SHA-256 与 revision；不要混用两轮证据的证明范围。

## 两分钟介绍顺序

1. **目标与范围**：为配置／元数据学习场景实现可恢复、强一致的小型 KV；固定三个 voter、单 Raft Group。
2. **关键契约**：写入先持久化复制，再多数派提交与应用后确认；读通过 ReadIndex 防止隔离旧 Leader 返回旧值；超时写入保留结果未知语义。
3. **一次具体优化**：可选后台磁盘路径中，繁忙副本返回 BUSY 后触发约 500 ms 重试等待；通过受控闸门定位，再增加有界等待和磁盘完成后的重新准入。
4. **结果与取舍**：同期新旧对照改善小状态尾延迟，但大状态未达减半门槛，因此保留同步默认值；另完成六小时稳定性与阶段恢复，不把它说成容量测试。

受控机制实验与云端性能实验应分开解释。实际云端二进制在本机受控闸门下，释放闸门至确认从 411.490 降至 6.458 ms；该数值不代表云端自然请求延迟。简历推荐使用正式三机对照的 491.046→46.344 ms，避免重复堆放不同口径。

## 优先准备的追问

| 追问 | 回答应覆盖的要点 |
| --- | --- |
| 为什么 GET 不能直接读 Leader 的 map？ | 节点可能已被隔离或丢失多数派；区分自认为 Leader、本轮多数派确认、当前任期提交和已应用位置。诊断 status 不提供业务强一致读语义。 |
| 写入什么时候返回成功？ | 区分接收、持久化、复制、多数派提交、状态机应用和响应；任意阶段的超时不能推导为未执行。request ID 只做传输关联，没有持久化去重。 |
| 后台线程怎样保持 Raft 顺序？ | 单磁盘消费者、任务数据所有权、有界预算、stream／sequence、准备／完成状态转换；高任期立即隔离旧身份，旧任务完成也不能复活旧 Leader 或误确认客户端。 |
| 为什么用有界等待，而不是立即重发？ | 解释 BUSY 与既有在途重试机制的组合；两槽／单来源／300 ms、弱连接、过期和断连清理；重新准入后仍需落盘，不能提前 ACK。 |
| 既然优化明显，为什么没有默认开启？ | 小状态改善不代表全部门槛通过；15 MiB P99.9 仍约 245 ms，默认同步控制也有尾部；需要继续归因和同期复测。 |
| 快照如何防止数据丢失？ | 冻结已应用边界、保留其后日志、文件同步／rename／目录同步、代次恢复与分块安装；区分快照编码线程和磁盘执行线程。 |
| CAS 怎样防 ABA？ | 使用成功修改的已提交日志索引作版本；删除后重建产生更高版本；比较失败仍可占用日志位置；旧快照版本迁移需确定性处理。 |
| 如何证明正确性？ | 确定性消息／时钟模拟、真实进程强杀／隔离／慢盘／I/O 故障、PUT／GET／DEL 与 revision／CAS 有界历史模型、重启与语义负例；说明有限覆盖边界。 |
| P99.9 和“零失败”怎样统计？ | 从原始逐请求记录重算分位数；三轮统计量的中位数不是合并分位数；已发失败与未发时刻分开；客户端共置与每连接一个在途请求限制结论。 |

源码阅读建议按网络／RPC → `cluster::Server` 请求调度 → `Node`／`RaftLog` → `FileStore` → `ReadIndex`／快照 → 后台持久化与有界副本等待的顺序进行。对照测试阅读，尤其是 [ReadIndex 真实进程测试](../tests/test_read_index.py)、[异步持久化测试](../tests/test_async_persistence.py)、[副本屏障测试](../tests/test_peer_deferred.py)和 [revision 故障历史](../tests/test_revision_faults.py)。

## 表述边界与投递准备

可以写“C++ 分布式 KV”“强一致读写”“可选后台持久化”“故障与恢复验证”。当前未实现 LSM／SSTable、SQL、Multi-Raft、在线分片、动态成员变更、跨 key 事务、Watch、TLS 或身份认证；不使用“完整数据库内核”“生产级”“百万 QPS”“多日无泄漏”“全服务 TSan 通过”等超出现有证据的表述。

投递前能够手画读写与恢复路径、解释上述一次优化并阅读对应测试即可。项目不要求现场演示；保留构建与复算入口，准备一两处可展开的源码和一个失败后调整决策的例子。当前没有为投递继续新增功能或重跑云端长实验的必要。
