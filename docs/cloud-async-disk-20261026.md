# 三机后台磁盘执行对照：2026-10-26

本轮后台磁盘模式未达到性能收益门槛。固定负载下，1 MiB 冷数据的每轮 P99 中位数从 21.301 增至 53.023 ms，15 MiB 从 19.690 增至 46.805 ms，六组配对均变差；成功吞吐也下降。因此保留同步磁盘默认方式，先调查额外等待，再决定是否延长运行窗口。

正式 12 个 30 秒窗口共 360 秒计时，210,783 次已发请求全部成功，另有 5,217 / 216,000 个计划时刻未发（2.4153%）。每轮后整组重启，核对冷键、256 个热键与锚值 revision，12 次均通过。原服务的 512 个旧实验键和四个保护值、程序哈希与 PID 未改变；临时实验服务已全部停止。[逐请求样本、源码与独立复算](../benchmarks/published/cloud-async-disk-20261026/README.md)已归档。

## 比较方法

- 使用同一份 `66bd2a9` C++ 核心，只切换 `--disk-executor sync|background`；实际执行工具为 `21f5601`，GCC 13.3、RelWithDebInfo，云端构建关闭测试。核心前阶段普通／ASan＋UBSan 各 186 项、组件 TSan 31 项及 CI 已通过。
- 固定 `--snapshot-encoder background`、journal、ReadIndex、adaptive、128 条／1 MiB 快照触发和 4 MiB journal 检查点阈值。固定 Leader 为节点 2；每轮创建新的独立数据目录。
- 冷 value 净负载为 1 MiB／15 MiB（128／1920 个 8192 B 值），热数据为 32 个连接各八个 128 B 值。32 连接、600 offered rps、50% 写，预热 1 秒。实际计时请求为 105,210 PUT、105,573 GET；预载、预热和恢复读不计入请求吞吐。
- 每档三组配对，1 MiB 按“同步／后台、后台／同步、同步／后台”执行，15 MiB 反向排列。每组窗口来自同一次约十分钟活动，不能视为跨天独立重复。
- 完全不传追踪参数，不创建追踪记录器。600 rps 是计划到达率，每连接最多一个未完成请求；忙时未发计划时刻单列，不能据此宣称生产容量或严格开放环延迟。
- 现有三台 ECS 均为两个逻辑 CPU，Linux MemTotal 约 3.54 GiB，CPU 型号报告为 Intel Xeon Platinum，Ubuntu 24.04／Linux 6.8。每个实验节点服务限一个 CPU／512 MiB；C++ 发压与控制程序共置 Follower 3，所在服务也限一个 CPU／512 MiB。原服务继续运行，未增加第四台机器或改变原服务 CPU 亲和性。

正式活动为 2026-10-26 10:14:09–10:24:17（Asia/Shanghai），墙钟约 607.696 秒，包括预载、预热、重启与核对。此前另做两轮两秒预检，2,400 次请求成功、0 未发时刻、两次重启检查；不合并到正式结果。

## 资源与解释边界

CPU 以一个逻辑 CPU 为 100%，从同一进程的 Linux ticks 与所属机器的单调时钟计算，按采样时长加权；RSS 为五秒间隔采样中观察到的最大值。

| 冷数据 | 磁盘方式 | Leader 平均 CPU | Leader 采样最大 RSS MiB | C++ 发压器平均 CPU |
| --- | --- | ---: | ---: | ---: |
| 1 MiB | 同步 | 9.24% | 15.45 | 4.58% |
| 1 MiB | 后台 | 12.25% | 16.78 | 4.60% |
| 15 MiB | 同步 | 10.38% | 134.38 | 5.11% |
| 15 MiB | 后台 | 14.24% | 101.53 | 5.29% |

资源区间包含热键预载、预热与最终排空，和纯计时窗口不完全重合；发压器 CPU 不包含 Python 控制进程。RSS 采样不是实际峰值，大数据组的较低采样值不能推广为内存优化结论。机器仍共享副本、发压与原服务资源；较低平均 CPU 也不能排除瞬时调度或配额等待。

本轮关闭追踪，只测量客户端结果、资源与状态计数，不能直接把后台组约 0.5 秒尾部归因为磁盘或线程切换。代码审阅提供了一个待验证的方向：

- [后台 Node](../src/raft/node_async.cc) 在已有磁盘屏障时可能拒绝新的副本请求并返回 BUSY；这满足确认顺序，但会改变请求等待的位置。
- [PeerWork](../src/cluster/server.cc) 遇到非 OK RPC 结果会关闭连接并继续，未把失败立即反馈给 Raft 的复制进度。
- [Node::Tick](../src/raft/node.cc) 按 [默认十个逻辑 tick](../src/raft/node.h) 释放超时的在途请求，服务 tick 名义间隔 50 ms。约 500 ms 的重试尺度与本轮尾部相近，仍需任务／RPC 的关联或可控繁忙副本实验才能确认为本轮原因。

下一步应先记录 BUSY／传输失败的次数及对应序号，用可控用例验证重试间隔，再评估有界等待或带退避的失败反馈。不能通过提前确认、无界排队或无退避重发来换取表面吞吐。完成后重跑同一矩阵，收益明确再启动较长窗口。

## 恢复、测试修正与证据

每轮计时结束后先等待复制／应用收敛，再仅停止本实验三节点，以同一配置重开。核对该轮所有冷值、由 C++ 请求序列独立重建的 256 个热值、锚值及其 revision；恢复记录保存逐值长度、SHA-256 和 revision。12 个正式轮次加两个预检轮次全部通过，不涉及原服务目录的升级或降级。

云端工具提交首次 push CI 出现一项失败，原因是复用的读测试要求新鲜读确认与新日志必须同包。后台路径可以先确认旧的持久前缀，再等先前 PUT 的应用位置，因而该合并指标允许为零。`29c6724` 修正测试口径：保留同步路径原断言，后台路径检查新鲜多数派请求、同任期、50 条 PUT 的日志数量和每个 GET 的值；磁盘闸门用例进一步要求多数派确认已启动而 GET 尚未完成。生产 C++ 没有因此改动，云端全程使用同一个程序。

本机相关普通三项／ASan 两项分别通过（34.99／38.41 秒），七项计划／参数检查通过；修正后 [push CI](https://github.com/ContinueForever/yeyu/actions/runs/40258911391) 和 [PR CI](https://github.com/ContinueForever/yeyu/actions/runs/40258918810) 的完整普通／ASan 187 项及其他任务全部通过。首次失败、测试补丁与修正后输出均保留；五项离线负例会刷新文件哈希及声称的原始哈希，仍须拒绝伪造 P99、执行模式、CPU 计数、恢复值与请求日历。

原始客户 gzip 样本和无身份信息的数值文件保持字节不变；诊断里的私网地址、主机名和路径映射为示例，映射前后哈希明确列出。只公开四个原服务保护值集合的哈希，不公开业务值或控制凭据。核验脚本使用当前仓库代码，源代码归档用于核对，不作为可执行的自证工具。

这次结果支持继续保留同步磁盘默认方式，并优先调查后台路径的额外等待；它不提供多日稳定性、真实断电、独立发压容量或其他负载下的性能结论。
