# 磁盘繁忙时的副本请求等待

`--disk-executor background` 将磁盘工作交给有序工作线程。副本执行本地检查点时，新的复制请求需要等待该屏障完成；如果直接返回 BUSY，旧传输路径关闭连接后不会立即释放 Raft 的在途请求。默认十个逻辑 tick、服务名义每 tick 50 ms，因此即使磁盘已经空闲，复制仍可能等到约 500 ms 后才重发。

本机可控实验只阻塞一个 Follower 的检查点，临时隔离另一个 Follower，使新写入必须等待被阻塞的副本；记录实际 TCP 请求、响应与序号。修复前 BUSY 响应到下一次复制请求约 503 ms，解除闸门到写入确认 424 ms。修复后的同类实验中，解除闸门到确认约 4 ms，没有 BUSY 响应，整组重启后写入存在。这证明此构造条件下的等待机制，不能直接代替三机性能复测，也不能把上一轮所有慢请求归为同一原因。

## 有界等待

服务的 Raft 所有者线程先调用 `ReceiveAsync`，让合法高任期消息立即撤销旧领导身份。若只是磁盘屏障拒绝了准入，保存请求的独立副本、弱连接引用和截止时间：固定三个投票节点下，每个远端节点最多一个等待请求，总计最多两个。请求大小继续受原有 Append／快照片段与 RPC 上限约束。

磁盘完成唤醒所有者后，先重试这些副本请求，再处理新的任务及本地快照。重新准入仍由 Node 执行全部任期、日志和持久化检查；只有所需屏障完成，才发送原协议回复。没有提前确认、所有者等待磁盘或无退避重发。队列已满时仍先处理高任期撤销，再返回 BUSY。

等待上限为 300 ms，给现有 400 ms 传输超时留下响应时间。准入前过期返回 UNAVAILABLE；连接关闭就移除。已经准入的操作仍遵循原来的持久化和未知结果语义。极慢磁盘、网络错误、队列满等情形仍可能触发原有复制超时；本次没有修改 Raft 的超时或多数派规则。

## 观测与验证

状态 JSON 增加下列累计计数。它们不启用逐请求追踪：

| 字段 | 含义 |
| --- | --- |
| `peer_deferred`／`peer_deferred_pending`／`peer_deferred_capacity` | 累计进入、当前等待数和总容量 |
| `peer_deferred_admitted` | 等待后成功准入，回复仍可能等待后续磁盘屏障 |
| `peer_deferred_expired`／`peer_deferred_abandoned`／`peer_deferred_rejected` | 准入前超时、连接关闭、无法等待而拒绝 |
| `peer_deferred_wait_ns`／`peer_deferred_wait_max_ns` | 成功重新准入前的累计／最大等待时间 |
| `peer_busy_received`／`peer_rpc_failed` | 发送线程收到的 BUSY 和失败调用；BUSY 也计入失败调用 |

`cluster_peer_disk_barrier` 使用仅在测试中预加载的磁盘闸门，覆盖检查点期间不提前确认、完成后继续复制、两槽及单来源上限、高任期即使溢出也立即撤销并最终持久化，以及超时／断连清理。原有异步崩溃、读写顺序、CAS、快照、故障恢复测试继续执行。

云端对照计划使用相同环境、后台 KV 编码器、无追踪、32 连接与 600 offered rps，比较旧后台程序、新后台程序和新同步程序。1／15 MiB 各三轮，三种顺序位置均衡，共 18 个 30 秒窗口，每轮独立目录并整组重启核对冷键、热键与锚值 revision。发压仍与 Follower 3 共机，不能宣称独立容量。

长运行计划复用六小时、六阶段、360 个一分钟窗口，轮换 0%／50%／90% 写入和 1／8／15 MiB 冷数据，明确记录磁盘执行模式。每阶段结束后整组重启验证，原服务保护与磁盘／内存预算仍生效。同步方式继续作为默认；实际结果应以运行完成后的证据报告为准。
