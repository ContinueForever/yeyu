# 三机持久化与慢读关联：2026-10-25

这轮补齐了“持久化发生在何时、哪些读请求同时等待”的证据。正式活动为 **12 个 30 秒窗口、360 秒测量、212,268 次已发请求成功、0 次失败**，另有 **3,732 / 216,000 个计划时刻未发出（1.727778%）**。开启追踪的 **53,065 个 GET 全部成功关联**，没有缺失、歧义或记录丢弃。同步／后台编码两组各完成一次整组重启后的值与 revision 检查。

观察支持继续研究有序后台磁盘发布：客户端耗时至少 20 ms 的 GET 中，Leader 同一工作线程上持久化区间与服务端接收至响应就绪区间的交集，占累计区间时间的 **59.82%／65.69%**。这不是预计可消除的延迟比例；文件同步的墙钟区间也包含调度等待。追踪增加了 CPU 消耗，后台编码组的 P99 中位数也变差。默认仍关闭追踪，后台磁盘发布尚未实现。

## 版本、环境与负载

运行源码固定在 `27baea4d528ee3d372b6b523996f36508c6ca16b`。运行时源码包 SHA-256 为 `95151689cde6120c63071f8c41d6fb8b6f15bfed75a4c20ce37ab25d8c723c5e`，节点二进制为 `eee89c3092f9c092c139371b4ff5fe977b0edf7eb524282aebc3cd16cf4a1b03`；发压器与实际编排工具的摘要均在[执行记录](../benchmarks/published/persistence-trace-20261025/control/execution.json)。

三台 ECS 均为 2 vCPU、Intel Xeon Platinum、Ubuntu 24.04，云端使用 GCC 13.3.0、RelWithDebInfo，云构建未运行 CTest。开发机 GCC 15.2.0 的普通 RelWithDebInfo 与 ASan/UBSan Debug 完整回归各 **154/154** 通过，耗时 66.34／81.60 秒，sanitizer 运行开启泄漏检测。核心提交的 [push CI](https://github.com/ContinueForever/yeyu/actions/runs/40203731890) 和 [PR CI](https://github.com/ContinueForever/yeyu/actions/runs/40203736735) 均通过。不同工具链与构建配置的范围分别保留，不把云负载当作云端完整回归。

每个实验节点限制 1 核 CPU、512 MiB；控制程序和 C++ 发压子进程共用另一个 1 核／512 MiB 控制组，部署在 Follower 3 所在机器。原有服务继续运行。没有独立发压机，也没有采集 CPU 限流事件，因此结果包含资源竞争，不能当成独立服务器容量。

sync 与 background 各使用新目录，预装 1,920 个 8 KiB 冷 value（15 MiB）。默认 adaptive 策略、128 条／1 MiB 触发阈值、4 MiB journal 检查点、ReadIndex 与 1,500 ms 超时保持一致。每组固定同一节点进程、Leader 2 和任期，依次运行 **关／开／开／关／关／开** 六个窗口：32 连接、计划 600 次／秒、50% 写入、128 B 热 value、256 个热键，另有每窗口 1 秒预热。

两组都启用 `--trace-identity 1`；预装、预热和测量调用的随机高位请求编号区间经检查无重叠，正式 384 个、烟测 128 个连接区间单独计数。这会增加部分 Protobuf 编号的编码长度，不能与早期小编号负载直接比较并宣称无开销。两组都创建了追踪器，关闭组通过控制文件暂停事件记录，控制线程和有界队列仍存在；本轮测动态开关的增量成本，没有测默认不创建追踪器的基线。追踪开时 `sample_every=1`，共享 500,000 事件／256 MiB 文件限额；三节点的开关状态均在每窗口前后确认。

正式活动于北京时间 **22:57:22—23:05:11** 执行，墙钟总时长 469.689 秒包含预装、预热、核验与重启，360 秒仅为测量窗口之和。烟测另有 4 个 2 秒窗口、4,723 次成功请求、77 个未发计划时刻，不混入正式结果。

## 慢 GET 与同线程持久化区间

关联通过客户端本地端口及请求编号完成。只在 **Leader 自己的单调时钟**内，把实际处理该 GET 的工作线程 TID 上持久化区间取并集，再与 `received_ns → ready_ns` 相交；队列等待与处理阶段的交集分别保存。没有相减客户端和服务端、或不同节点的单调时钟。

正式开启组共 26,473／26,592 个 GET，全部关联；关闭组没有读追踪，覆盖为 0，不能据此认为关闭时没有持久化等待。24 个进程生命周期日志（含烟测与重启后空日志）均有完整退出摘要，合计 291,413 条已写数值事件，丢弃、限额、I/O 失败及截断均为 0；文件、事件上限均未触发。

慢请求按 **客户端实际 RPC 耗时 ≥20 ms** 选取，下列比例的分母是该组慢 GET 的服务端 `received → ready` 时间总和。各请求先做区间并集再求和，并发请求可重复覆盖同一磁盘操作；这不是磁盘利用率或独占 CPU 时间。

| 关联范围 | sync | background |
| --- | ---: | ---: |
| 已关联慢 GET | 995 / 995 | 929 / 929 |
| 与持久化有交集的慢 GET | 981 | 927 |
| 慢 GET 的服务端区间累计秒数 | 51.943 | 41.597 |
| 整次持久化区间交集占比 | 59.82% | 65.69% |
| 其中：进入处理前排队的交集 | 27.11% | 25.17% |
| 其中：进入处理后至响应就绪的交集 | 32.70% | 40.53% |
| 文件同步阶段交集 | 43.45% | 52.67% |
| 编码阶段交集（含 CRC） | 11.62% | 9.65% |
| 写入阶段交集 | 3.27% | 2.11% |
| 目录同步阶段交集 | 0.60% | 0.54% |
| rename 阶段交集 | 0.48% | 0.43% |

整次持久化包含少量未细分操作，所以各 I/O 阶段之和略小于整次持久化交集。CRC 已包含在编码阶段，不重复相加。`fdatasync` 阶段记录的是调用及相邻计数操作的墙钟区间，会包含线程被调度出去、CPU 配额等待等时间，不能直接称为纯设备耗时。

本记录还未覆盖 KV 序列化／冻结、journal 后缀 payload 预构造、恢复路径中的全部直接 I/O，也没有归因 Follower 持久化、网络与调度。即使追踪开启且没有丢记录，未插桩阶段仍存在。交集说明请求等待与本线程持久化同时发生，不能证明这些时间能由异步化全部消除。

## 正确性、恢复与异常记录

核心回归包括追踪开关前后的持久磁盘字节等价、回调异常隔离、真实 I/O 失败不会确认成功、有界记录器，以及真实三进程读关联和整组恢复。154 是当前 CTest 用例数，关联工具的内部断言或公开证据语义负例不另加到这个数上。

正式 sync／background 各在结束后整组重启，检查全部 1,920 个冷键、256 个热键及锚值 revision；烟测同样另做两次恢复检查。原服务始终运行，实验前后 512 个既有实验键和 4 个保护值一致，节点程序摘要、重启计数与 CPU 亲和性保持原状。实验控制、代理、节点和发压服务均已停止，清理无错误。

开发中有一次新测试把集群对象的 `stop` 事件当成方法调用，修正测试结束流程后执行了最终完整 154 项回归。首次正式启动门槛则在本地编排中把 node 2 的日志路径拿到 node 3 读取，未能通过；修正为分别收回客户端样本和 Leader 日志、在本地关联后再启动正式活动。[门槛修正记录](../benchmarks/published/persistence-trace-20261025/control/setup-recovery.json)明确保留此事。未重放烟测，没有丢弃或重跑正式窗口。

## 复算与下一步

全部样本、数值追踪、执行工具、运行源码、测试源码与回归日志见[证据入口](../benchmarks/published/persistence-trace-20261025/README.md)。本轮运行记录的 IP、主机名、私有路径和实验服务标签统一替换；冻结源码保留提交原文中的静态测试样例。数值 JSON、客户端 gzip 和追踪 JSONL 保持原始字节，核验器同时核对原始导出摘要与公开文件清单。归档中的程序只做内容核对，不执行。

```bash
python3 scripts/verify-persistence-trace.py benchmarks/published/persistence-trace-20261025
python3 tests/test_persistence_evidence.py
```

核验器重算 12 个正式窗口和 4 个烟测窗口，检查全部编号区间、开关、进程／任期、日历、实际混合、资源、计数差分、24 个日志退出摘要、逐 GET 交集及恢复。负例即使刷新内外文件摘要，也必须拒绝错误开关、超出持久化操作的阶段区间和被低报的未发请求数；归档路径越界另有检查。CI 对公开证据持续执行同样校验。

接下来实现有序后台磁盘发布时，先把“可计算状态”和“已落盘、可对外确认状态”拆清楚：term/vote、复制响应、客户端成功和快照／journal 代次均须保持原有持久化先行条件；队列必须有界，磁盘失败要停止确认。先过强杀、故障注入和恢复测试，再用同负载重复比较尾部与未发时刻。本轮只完成了诊断依据，独立发压、多轮长对照、多日运行和真实断电仍需后续验收。
